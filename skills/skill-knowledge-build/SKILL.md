# スキル作成のための知識構築（skill-knowledge-build）

ある分野のスキル（手順書）を作るときに、土台となる知識を「より広く、
より横断的に、より深く」構築してからスキルへ落とし込むための方法。
知識が薄いまま手順だけ書くと、平凡で漏れの多いスキルになる。逆に、
知識の母集団を先に大きく作ってから選別・構造化すると、スキルの
質は知識の質で決まるようになる。

中核の進め方: 分野を地図に分け、分野ごとにサブエージェントを並行で
走らせて Web 検索で知識を集め、親が統合・矛盾解決・抜け漏れ監査を
してから、対象スキルの構造へ反映する。

## いつ使うか

- 新しい分野のスキルを新規に作るとき
- 既存スキルを「もっと良いもの」に作り直したいとき（知識の不足が原因で
  成果物の質が頭打ちになっている場合）
- 「あらゆるものを調査してスキルにして」のような網羅要求があるとき

小さな手順メモ程度のスキルには使わない。知識構築のコストに見合うのは、
繰り返し使う中核スキルだけ。

## 基本原則

1. **知識が先、手順は後。** 作るもの（スキルの章立て・項目）を決める前に、
   その分野の知識の母集団を作る。ただし「何のためのスキルか」という
   目的と利用場面だけは先に固定する（目的が無い調査は散らかる）。
2. **広さ × 深さ × 横断。** 広さ＝分野の抜けが無いこと。深さ＝各項目が
   「具体的な設定値・手順・判定基準」まで降りていること。横断＝分野同士の
   接続（ある分野の原則が別の分野の失敗を防ぐ等）が言語化されていること。
   どれか1つ欠けるとスキルは偏る。
3. **項目は実務形式で集める。** 1項目は必ず
   「何をするか／なぜ効くか（仕組み）／どう適用するか（数値・手順）／出典」
   の4点セット。感想や一般論の項目は数えない。
4. **出典必須。** Web 検索で裏を取り、公式ドキュメント・一次情報を優先する。
   出典の無い知識は「未検証」と明示して分ける。
5. **サブエージェントの自己申告は信じない。** 「検証済み」「重複なし」
   「網羅した」は全て未確認の主張として扱い、親が自分で読み戻し・
   目視・再計測してから完了と言う（過去に複数回、自己申告と実物が
   食い違った教訓）。
6. **数は質の後。** 項目数の目標は足切りではなく母集団の規模感。
   質の低い項目で枠を埋めない。分野によっては集まった量に差が出てよい。

## 手順

### 手順0: 目的と既存資産の固定

- 対象スキルが「誰の・どんな作業を・どう良くするか」を1〜3行で書く。
- 既存のスキル・資料・過去の成果物と、その既知の弱点（ユーザーの却下理由や
  失敗の記録）を棚卸しする。弱点は調査の重点分野を決める材料になる。
- 調査成果物の置き場を決める: `~/workspace/research_notes/<対象>-knowledge-<日付>/`
  に分野ごとのファイルで残す（スキルへ反映した後も原典として残る）。

### 手順1: 分野マップを作る

対象分野を分野（サブドメイン）に分けた地図を先に作り、ユーザーに
見せてから調査に入る（大きな作業では承認を取る）。
分野の数は多めでよい。目安は8〜15、対象が広ければそれ以上に分けても
構わない。細かく分けるほど並行調査の網が細かくなり、抜けが減る。
ただし細かすぎると境界の重なりと統合のコストが増えるので、
「1分野＝サブエージェント1つが深く掘り切れる単位」で切る。

- 分け方: 制作物のライフサイクル（企画→制作→検証→公開）か、
  対象の構成要素（例: 音楽なら旋律／和声／声部／形式／編曲／場面）で切る。
- 必ず入れる横断分野: 「失敗パターンと対処」「検証・品質保証」。
  各分野の How だけ集めると、直し方と確かめ方が抜ける。
- 既存スキルがある場合は、その章立てとの対応も地図に書く
  （どの分野が既存のどこを補強し、どこが新規か）。

### 手順2: サブエージェント並行調査

分野ごとにサブエージェントを1つ割り当て、**全分野を同時に**走らせる。
1分野ずつ逐次でやると横断の視点が消え、時間もかかる。

各エージェントへの指示は「サブエージェント指示テンプレート」を使い、
次を必ず含める:

- 担当分野の範囲と、隣の分野との境界（重複を避けるため、担当外を明示）
- 項目の形式（基本原則3の4点セット）と目標量（目安15〜25項目）
- Web 検索の必須化と出典の付け方（URLを項目ごとに）
- 公式・一次情報の優先、ブログの伝聞だけに寄らないこと
- 成果物の保存先（分野ファイル）と報告形式
  （項目数と、最も重要な3項目の要約だけを報告させる。本文はファイルに）

エージェントは report-only にし、スキル本体は編集させない。
反映は親が一括で行う（並行編集は競合と表記ゆれの元）。

### 手順3: 統合と矛盾解決

親が全分野ファイルを読み、次を行う:

- **重複の統合**: 同じ原則が複数分野に出たら1つにまとめ、横断参照にする。
- **矛盾の解決**: 数値や推奨が食い違う項目は、出典の強さ（公式＞実測＞
  経験談）と、対象スキルに固有の条件（エンジン・規模・価格帯等）で判定し、
  判定理由を1行残す。両論併記で逃げない。
- **用語の統一**: 同じ概念の呼び方を1つに揃える。
- **対象への翻訳**: 一般論の項目を、対象の道具・ファイル・パラメータ名に
  置き換える（例: 「DAWで…」→ 対象ツールの具体名と値）。翻訳できない
  項目は知識ノート側に残し、スキルには入れない。

### 手順4: 抜け漏れ監査（2レンズ以上）

統合が終わったら、**調査に参加していない**サブエージェントに監査させる。
レンズは最低2種類:

- **網羅レンズ**: 分野マップと実務の全工程を見て、丸ごと抜けた分野・
  工程が無いか
- **質レンズ**: 成果物の品質（見栄え・面白さ・使い勝手の良さ等、対象の
  成功指標）に効く知識が薄くないか

監査は report-only。指摘が「重要な抜けあり」なら、追加調査（手順2へ
戻る）か、既存ファイルへの章追加で埋める。監査で問題が無くなるか、
残りが軽微になるまで繰り返す（実績では2周で収束）。

### 手順5: スキルへの反映

知識を対象スキルの構造へ落とす:

- 分野ごとに references ファイルを分ける（1ファイル1分野。巨大な
  単一ファイルにしない）。手順の本体は SKILL.md に置き、詳細知識は
  references へ、という分担を守る。
- SKILL.md の手順からは references の該当箇所を明示的に参照させる
  （「詳細は references/xxx.md」と書かない箇所は読まれない）。
- 項目は「原則→手順と具体設定→失敗と対処→チェックリスト」の順に並べる。
- スキルが複数に分かれる場合は索引ハブを1つ作り、全体地図と
  使い分けを示す。
- 機械化できる点検はスクリプトやチェックリストにして、知識を
  「読むだけ」で終わらせない。

### 手順6: 検証

親が自分で確認する（サブエージェントの報告で済ませない）:

- 全ファイルの存在、行数、見出し構成が設計どおりか
- skill.yaml 等のメタ情報が解釈できるか、スキル検索で発見できるか
- 相互参照（SKILL.md → references、ハブ → 各スキル）が実在のパスか
- 反映漏れ: 知識ファイルの全項目が、スキル側のどこかに行き先を
  持っているか（意図的に外した項目は理由を記録）
- 可能なら対象スキルを使って小さな成果物を1つ作り、知識が実際に
  効くか（手順が回るか）を確かめる

検証結果は「確認済み／直した点／未確認の点」を分けて報告する。

## サブエージェント指示テンプレート

```
あなたは「<スキル名>」の知識構築のため、分野「<分野名>」だけを調査します。

範囲: <この分野に含むもの>
担当外: <隣接分野。そちらは別エージェントが担当するので書かない>

進め方:
- Web検索で裏を取りながら、実務に使える知識を15〜25項目集める
- 公式ドキュメント・一次情報を優先する。出典URLを項目ごとに付ける
- 各項目は「何をするか／なぜ効くか／どう適用するか（具体値・手順）／出典」
  の4点セットで書く。一般論・感想は書かない
- 対象の条件（<エンジン／道具／規模など>）に引き付けて書く

成果物: <research_notes のパス> にMarkdownで保存する
報告: 保存先、項目数、最も重要な3項目の1行要約だけを返す。
      スキル本体（SKILL.md等）は編集しない
```

## よくある失敗と対処

- **集める前に作るものを決めてしまう**: 章立てを先に固定すると、
  調査がその枠の穴埋めになり、枠外の重要分野が永遠に抜ける。
  → 目的だけ固定し、章立ては知識が揃ってから決める。
- **サブエージェントの「網羅した」を鵜呑みにする**: 過去に画像収集で
  「重複なし・検証済み」と報告された成果物に、実際は重複や無関係な
  ものが多数混ざっていた。→ 親が実物を目視・再計測する。監査は
  調査者と別エージェントにやらせる。
- **出典の無い知識が混ざる**: もっともらしい一般論が紛れ込む。
  → 出典必須を指示に含め、統合時に出典なし項目を落とすか
  「未検証」と明示する。
- **分野の切り方が成果物とずれる**: 教科書の分類で切ると実務の
  工程と合わない。→ ライフサイクルか構成要素で切り、横断分野
  （失敗・検証）を必ず足す。
- **反映で知識が薄まる**: 要約しすぎて数値や条件が落ちる。
  → references には知識ファイルの具体値をそのまま残し、SKILL.md の
  手順からは参照で引く。薄めるのは重複だけ。
- **1回の調査で終わらせる**: 最初の地図には必ず抜けがある。
  → 監査（手順4）を省略しない。2レンズで見て初めて出る抜けがある。
