# Breakthrough

ユーザーから渡された課題に対し、多数のサブエージェントを組織して深く考え、
**最適かつ革新的** な解を導き出す。

単体のエージェントが一度考えて出す答えは、もっとも「ありがち」な答えに収束しやすい。
このスキルの目的は、その収束を意図的に壊し、思考の探索範囲を広げ、
そのうえで厳しく選別して、実際に通用する非自明な解に到達することにある。

## 基本原則

- **ありがちな答えを先に言語化して、それを基準線（ベースライン）にする。** ベースラインを超えない案は採用しない。
- **発散と収束を混ぜない。** 発散フェーズでは批判しない。収束フェーズでは遠慮しない。
- **独立性を守る。** 発散フェーズのエージェント同士には互いの案を見せない。見せると全員が同じ方向に寄る。
- **多様性は「指示の違い」からしか生まれない。** 同じプロンプトを複数回投げても似た答えしか返らない。エージェントごとに思考レンズ・前提・視点を明確に変える。
- **前提を疑う。** 課題文に書かれた制約のうち、本当に動かせないもの（硬い制約）と、慣習で置かれているだけのもの（柔らかい制約）を分ける。革新は大抵、柔らかい制約を外したところから生まれる。
- **最終的には実行可能性で裁く。** 斬新さは手段であって目的ではない。効果・実現性・コストで勝てる案を選ぶ。

## サブエージェントの扱い

- サブエージェントは会話の文脈を持たずに起動する。**プロンプトは毎回自己完結させる。** 課題の要約、目的、硬い制約、ベースライン、そのエージェントの役割、出力形式をすべて含める。
- 互いに依存しない呼び出しは **1つのメッセージ内で並列に** 発行する。
- 調査・コード読解が必要な場合は `Explore`、それ以外の思考タスクは `general-purpose` を使う。
- 各エージェントには出力形式を指定し、統合しやすい構造で返させる（後述のテンプレート参照）。
- サブエージェントの結果は捏造しない。返ってくるまで待つ。

## 規模の決め方

課題の難しさと影響範囲に応じて規模を選ぶ。ユーザーが指定した場合はそれに従う。

- **標準（既定）**: 発散 6〜8 体、交配 2〜3 体、批判 2〜3 体、進化 1 ラウンド
- **深掘り**: 発散 10〜12 体、交配 3〜4 体、批判 3〜4 体、進化 2 ラウンド
- **軽量**: 発散 4 体、交配 1 体、批判 1〜2 体、進化なし

開始時に、選んだ規模を一行でユーザーに伝える。

## 手順

### フェーズ 0: 課題の定式化（自分で行う）

サブエージェントを起動する前に、以下を整理する。

1. **真の目的**: 課題文の表面ではなく、それが解決されると何が嬉しいのか。「なぜ」を2〜3回掘り下げる。
2. **成功基準**: 何をもって「最適」とするか。評価軸（例: 効果、実現性、コスト、速度、保守性、リスク、拡張性）と、その重み付け。
3. **制約の仕分け**: 硬い制約（物理法則・法令・ユーザーが明示した絶対条件など）と、柔らかい制約（慣習・現状の仕組み・暗黙の前提）。
4. **ベースライン**: この課題に対して誰もが最初に思いつく答え、業界の定番解を1〜3個、具体的に書き出す。
5. **未知の点**: 判断に必要だが分からない事実。

目的や硬い制約が曖昧で、解釈によって答えが大きく変わる場合に限り、AskUserQuestion でユーザーに確認する。
それ以外は合理的な仮定を置いて進み、仮定は最終報告に明記する。

### フェーズ 1: 現状把握（必要な場合のみ）

課題が既存のコードベース・既存技術・事実関係に依存する場合、調査エージェントを並列に起動して以下を集める。

- 現状の仕組みとその本当のボトルネック
- 既知の解法・先行事例・最新の手法（既にあるものを「新発明」と誤認しないため）
- 関連する数値・制約の実測値

調査結果でフェーズ 0 の定式化（特にベースラインと制約）を更新する。

### フェーズ 2: 発散（並列・独立）

発散エージェントを並列に起動する。各エージェントに **異なる思考レンズ** を1〜2個割り当てる。
課題に合わせて、下のレンズ一覧から互いに遠いものを選ぶ。同じ系統のレンズばかりにしない。

各エージェントへの指示に必ず含めること:

- ベースラインを明示し、「これと本質的に同じ案は出さない」と指示する
- 3〜5 案を出させる。うち少なくとも1案は「常識的には馬鹿げて見えるが、筋が通るかもしれない」案にさせる
- 実現性の自己検閲をしないこと（批判は後のフェーズで行う）
- 各案について、なぜそれが機能しうるのかのメカニズムを書かせる（単なる思いつきの羅列を防ぐ）

#### 思考レンズ一覧

- **第一原理**: 課題を物理的・論理的な最小要素まで分解し、既存の解き方を忘れて組み立て直す
- **逆転**: 問題を裏返す。「どうすれば最悪にできるか」を考え、それを反転する。主従・順序・方向を逆にする
- **遠隔アナロジー**: 無関係な分野（生物、生態系、物理、経済、軍事、物流、建築、言語、ゲーム、宗教儀礼、歴史など）で同型の問題がどう解かれているかを探して移植する
- **制約除去**: 柔らかい制約を1つずつ外す。「予算無限なら」「時間ゼロなら」「既存資産を全捨てしてよいなら」
- **制約追加**: あえて厳しい制約を課す。「コスト1/100なら」「人手ゼロなら」「1行で書くなら」
- **極端スケール**: 規模を 1000 倍、または 1/1000 にしたときに成立する解を考え、それを現実に持ち帰る
- **削除**: 構成要素を1つずつ取り除いても目的が達成できないか考える。最良の部品は存在しない部品
- **理想最終解（TRIZ）**: 「何もしなくても目的が勝手に達成される状態」を描き、そこから逆算する
- **矛盾の解消**: 「Aを良くするとBが悪くなる」というトレードオフを特定し、妥協ではなく両立させる仕組みを探す
- **時間軸の移動**: 処理・判断・コストを前倒し・後回し・分散・事前計算する。10年後の技術前提で考える
- **主体の移動**: 誰が・何がその仕事をするかを変える（ユーザー、相手、環境、機械、市場、自然現象）
- **結合と分割**: 別々のものを1つにまとめる。1つのものを独立した部分に分ける
- **逆張り**: 業界の常識・ベストプラクティスとされているものを1つ選び、その逆が正しい世界を仮定する
- **敵対者視点**: 競合・攻撃者・怠惰な利用者・未来の保守担当者の立場から、現状と代替案を見る
- **新人の視点**: 専門知識を持たない賢い外部者として、「なぜそもそもこうしているのか」を素朴に問う

### フェーズ 3: 交配と変異（並列）

発散フェーズの全案を集め、重複を統合して一覧（案ごとに1〜3行の要約＋メカニズム）を作る。
交配エージェントにその一覧を渡し、次のいずれかを担当させる。

- 異なる案の **組み合わせ** で、単独の案より強い案を作る
- もっとも突飛な案を **さらに押し進め**、現実に着地する形を探る
- 有望だが弱点のある案の **弱点だけを置き換える**
- 全案に共通して欠けている視点を指摘し、その穴を埋める案を出す

### フェーズ 4: 批判（並列）

ここまでの候補から、評価軸に照らして有望なもの 3〜6 案を選ぶ。斬新さだけで落とさず、
ベースラインを明確に超えうるものを残す。

批判エージェントを起動し、候補を徹底的に攻撃させる。役割を分けると効果が高い。

- **実現性の検証者**: 技術的・物理的・組織的に本当に実現できるか。隠れた前提は何か
- **コストと副作用の検証者**: 隠れたコスト、二次的影響、運用負荷、移行コスト
- **失敗モードの検証者**: どういう条件で破綻するか。最悪ケースは何か
- **新規性の検証者**: それは本当に新しいか。既存の手法の言い換えではないか。ベースラインを本当に超えているか

批判には「致命的（解決不能）」「重大（要対策）」「軽微」の区分を付けさせ、
致命的でないものには対策案も添えさせる。

### フェーズ 5: 進化

批判を受けて、生き残った案を改良する。致命的な欠陥がある案は捨てるか、
欠陥を回避する別の形に作り変える。改良は、案ごとに1エージェントを並列に割り当てる。

深掘り規模では、改良後の案に対してフェーズ 4 と 5 をもう一度繰り返す。

### フェーズ 6: 収束と判定（自分で行う）

フェーズ 0 で定めた評価軸と重みで、最終候補とベースラインを並べて評価する。
評価が拮抗する場合や自分の判断に偏りが疑われる場合は、独立した審査エージェントを複数起動して
採点させ、結果を突き合わせてもよい。

最終案は、次の条件をすべて満たすものを選ぶ。

- ベースラインを評価軸で明確に上回る
- 致命的な欠陥が残っていない
- 最初の一歩を具体的に踏み出せる

## 最終報告の形式

ユーザーへの報告は以下の構成にする。

1. **結論**: 推奨案を数行で。何が本質的に新しいのか、なぜベースラインより優れるのか
2. **推奨案の詳細**: 仕組み、なぜ機能するのか、前提条件
3. **ベースラインとの比較**: 評価軸ごとの比較
4. **次点の案**: 1〜3 案。推奨案と性質が異なるもの（例: 低リスク版、より野心的な版）を選ぶ
5. **リスクと対策**: 批判フェーズで出た重大な論点とその対策
6. **検証方法**: 推奨案が本当に機能するかを最小コストで確かめる実験・プロトタイプ・計測の手順
7. **置いた仮定**: フェーズ 0 で置いた仮定のうち、結論を左右するもの

途中経過（全案の一覧など）は、ユーザーが求めない限り報告に含めない。
ただし、捨てた案の中に「条件が変われば有力になる」ものがあれば一言触れる。

## サブエージェント用プロンプトのテンプレート

発散エージェントの例:

```
あなたは課題解決のための発想担当です。他の担当者とは独立に考えてください。

## 課題
<課題の要約>

## 真の目的
<目的>

## 硬い制約（動かせない）
<一覧>

## ベースライン（ありがちな答え。これと本質的に同じ案は出さないこと）
<一覧>

## あなたの思考レンズ
<レンズ名と説明>
このレンズを徹底して使ってください。実現性の自己検閲は不要です（後で別の担当者が検証します）。

## 出力形式
3〜5 案。少なくとも1案は、常識的には馬鹿げて見えるが筋が通るかもしれない案にすること。
各案について:
- 案の名前
- 内容（3〜5行）
- なぜ機能しうるのか（メカニズム）
- ベースラインとの本質的な違い
```

批判エージェントの例:

```
あなたは<役割>として、以下の候補案を厳しく検証します。遠慮は不要です。

## 課題・目的・硬い制約
<要約>

## 候補案
<案ごとの詳細>

## 出力形式
案ごとに:
- 指摘（各指摘に「致命的」「重大」「軽微」の区分を付ける）
- 致命的でない指摘への対策案
- 総合判定（採用候補に残すべきか、その理由）
```
