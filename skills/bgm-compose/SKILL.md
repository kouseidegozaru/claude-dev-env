# BGM作曲（bgm-compose）

ゲームBGMなどのインストゥルメンタルを、「作曲仕様書」から作る統合スキル。
作曲（仕様書→MIDI）、音源（実録サンプル楽器と GM 音源の台帳）、ギターの音作り
（実録 DI＋アンプ処理）を1か所にまとめる。生成AIの取り直しと違い、狙った
1フレーズだけを仕様書の書き換えで確実に直せるのが要点。

同梱物:

- `scripts/compose.py` — 仕様書（Python の辞書）から MIDI を生成する
- `scripts/render.py` — FluidSynth 描画、EQ 補正、loudnorm 2パス、ループ化、納品ゲートまで一括実行
- `scripts/render_mix.py` — 主旋律チャンネルだけを自作ピアノ音源で描き、他パートを GM で描く混合レンダラー（ピアノ主導の曲用）
- `scripts/measure.py` — 音響計測（LUFS / トゥルーピーク / 低域比 / スペクトル重心 / 継ぎ目段差）
- `scripts/check_midi.py` — 記譜上の機械確認（主題の戻り、音域、跳躍）
- `scripts/theme/` — 主題選別の前段一式（候補生成・校正済み検査器・回収テスト。手順0で使う）
- `scripts/render_sfz.py` — 汎用 SFZ レンダラー（SFZ 楽器とフォルダ楽器を鳴らす）
- `scripts/render_guitar.py` — 実録ギター DI サンプル専用レンダラー
- `scripts/dump_events.py` — ステム MIDI を音符イベント JSON に変換する
- `scripts/harmonize_template.py` — 単音リードをコードメロディ（和音）に変換する雛形
- `scripts/guitar_fx.py` — ギター音色プリセット集（歪み・モジュレーション・空間系）
- `references/patterns.md` — コード進行・伴奏型・構成型のパターン集と作曲技法
- `references/instruments.md` — 音源台帳（実録サンプル楽器と SF2/GM 音源、ライセンス込み）
- `references/guitar.md` — ギター制作の詳細（素材検品・和音化・歪みの目安・ジャンル別レシピ・トラブル対応）
- `examples/` — 仕様書の実例（曲型とループ型）
- `assets/forge_piano.sfz` — 自作ピアノ音源の設計（SF2 本体は 36MB のためリポジトリに含めない。台帳参照）

## 前提（最初に確認する）

- `fluidsynth`（2.x）と `ffmpeg` が使えること。
- 作曲と記譜確認は mido の入った venv の Python で行う: `~/workspace/midi-bgm/venv/bin/python`
- 計測は numpy の入ったシステムの `python3` で行う（render.py が自動で使い分ける）。
- 音源は `references/instruments.md` の台帳にあるものだけを使う。既定は FluidR3_GM
  （`/usr/share/sounds/sf2/FluidR3_GM.sf2`）。
- 前提の確認は render.py が入口の事前検査で自動で行う（実行ファイル・venv の Python・
  音源ファイル・仕様書と MIDI の存在）。不足があれば、何が無いかと復旧手順
  （再導入コマンドや `--sf` の指定など）を表示して描画に入らず即座に止まる（終了コード 2）。
  環境の再構築直後などは、この表示どおりに復旧してから再実行する。
  また FluidSynth は音源を読み込めなくても無音の WAV を正常終了で出すことがあるため、
  render.py は描画直後に無音・ノイズフロアだけの出力を検出して失敗として報告する。
  手で先に確かめたい場合は `which fluidsynth ffmpeg ffprobe` と
  `ls -l /usr/share/sounds/sf2/FluidR3_GM.sf2` で足りる。

作業ファイルは曲ごとのフォルダに置く（例: `~/workspace/midi-bgm/<曲名>/`）。
フォルダには仕様書、生成 MIDI、render.py の出力（完成 OGG と render_report.json）を残す。

## 手順0（任意の前段）: 主題選別

主題が印象を決める曲（タイトル曲や場面の顔になる曲）では、作曲の前に `scripts/theme/` の
主題選別を通し、主題を1案に絞ってから手順1へ進む。一発の作曲では主題の質に
担保が無いためで、実使用ではこの選別が目隠しで良い主題と平凡な主題を
分離できることを2回実測した（外部の名主題が1〜5位、平凡な対照が14位以下）。

流れ:

1. 初回のみ校正を確認する: `scripts/theme/calibrate.py` を実行し、権限のある検査器が
   `scripts/theme/calibration/calibration_record.json` と一致することを確かめる。
   権限の無い項目（モチーフ等）は警告としてのみ扱い、足切りには使わない。
2. 初回のみ回収テストで自分の選別を検証する: `scripts/theme/recovery_test.py` で
   目隠しプールを作り、譜面だけを見て全順位を付け、理由をファイルに固定してから
   採点する。名主題が上位に回収できなければ、その選別は未検証として扱い、
   主題選別に頼らない。
3. 候補を30〜60案生成する（`scripts/theme/generate_pool.py`）。手書きの主題も種として混ぜてよい。
4. 権限のある検査器で足切りする（`scripts/theme/theme_check.py`）。
5. 残った候補を、出自を隠した譜面シート（`scripts/theme/theme_sheet.py`）だけを見て
   順位付けし、本命1案と予備を理由つきで記録してから対応表を開ける。
   代理スコアで代用しない。
6. 選ばれた主題を手順3の仕様書の主旋律として書き、手順1以降は通常どおり進める。
   選別の記録（順位と理由）は曲のフォルダに残す。

適用範囲: 校正は長調の主題曲のみ。短調・環境曲では主題選別を使わず、
手順1から通常どおり作る（校正試料の追加が今後の課題）。

## 手順1: 仕様決定

場面ごとに、作り始める前に仕様書へ固定する:

- 長さの目安、ループ有無、BPM、調性、コード進行、構成（各セクションの小節数）、楽器編成
- **seed 欄は必須**。乱数の種を記録しない仕様書は不完全として扱う（compose.py がエラーにする）。
  同じ仕様書からはバイト一致の MIDI が再生成できる。
- 同場面の既存曲がある場合は基準として計測し、統合ラウドネス・低域エネルギー比・
  スペクトル重心を仕様書の近くに転記する:
  `python3 scripts/measure.py <既存曲.ogg>`
- 低域エネルギー比は音源ではなく編成でほぼ決まる。基準に寄せる必要がある場合は、
  ベースの音域・密度・持続を仕様の段階で合わせておく（patterns.md の「ベース型」参照）。

仕様書の形式は `examples/spec_spring_noon.py`（曲型）と `examples/spec_loop_lake.py`（ループ型）。

## 手順2: 骨格選択

`references/patterns.md` から実績のある型を選ぶ。進行・伴奏型・構成型を場面に合わせて組み合わせ、
迷ったら「場面→出発点の目安」の表から始める。型に無い進行を書くのは構わないが、
その場合は理由を仕様書のコメントに残す。

## 手順3: 作曲

メロディと各パートを音名（MIDI ノート番号）＋拍位置の表として仕様書に書き、MIDI 化する:

```
~/workspace/midi-bgm/venv/bin/python scripts/compose.py spec.py song.mid
```

- 伴奏・ベース・パッドは進行から自動生成される。主旋律は小節ごとの表で書く。
- ベロシティの強弱と微小なタイミングの揺らぎが seed で再現可能な形で入る。
- 単調さ対策（作曲技法調査を反映。詳細は patterns.md）: 伴奏は
  `pattern_cycle` で小節ごとにローテーションし、ベースは全音符型を既定にせず
  `root_5_8`／`approach` 等のパターンを使い分ける。仕様書に `ornament` を書くと
  主旋律へ経過音・刺繍音の装飾パスが掛かる。和声は予算制でセカンダリードミナントと
  借用和音を少量差し込み、パッドは 7th/add9 の色音を分担させる。
- 記譜の確認: `~/workspace/midi-bgm/venv/bin/python scripts/check_midi.py spec.py song.mid`
  主題の冒頭フレーズが再現部に逐語で戻っているか、音域と最大跳躍を機械確認する。

## 手順4: レンダリングとマスタリング

```
python3 scripts/render.py --spec spec.py --mid song.mid --out out --name song \
    --baseline <同場面の既存曲.ogg> [--sf <音源>] [--loop]
```

render.py が次を順に行い、`out/render_report.json` に全記録（段階ごとの所要時間つき）を残す:

0. 事前検査（前提の節参照）。不足があれば復旧手順を表示して即停止する。
1. FluidSynth で台帳の音源を使い WAV 描画（ピーク超過時はゲインを下げて描き直す）。
   描画直後に無音・ノイズフロアだけの出力を検出したら、後段の数値エラーにせず
   その場で失敗として報告して止まる。
2. 基準曲を計測して baseline.json を作る。
3. 低域比が基準の許容（±10pt）から外れていれば、lowshelf EQ（180Hz）を ±3.5dB ずつ
   「測定→補正→再測定」の反復（最大2回）で寄せる。補正は必ず生描画から当て直す。
4. 音量正規化は目標固定: **統合ラウドネス -14 LUFS、トゥルーピーク -1 dBTP 以下**。
   loudnorm は1パス目で測定し、測定値を使った2パス目の線形補正で当てる
   （パラメータ無しの loudnorm は使わない）。符号化後のトゥルーピークが上限を
   僅かに超えることがあるため、その場合は loudnorm の TP 目標を下げて当て直す
   （render.py が自動で最大2回まで調整する）。
5. ループ指定時は末尾クロスフェード版も作り、継ぎ目を計測する（ループ型の扱い参照）。
6. 納品ゲートと記譜確認を実行する。

### 手順4b（任意）: ステムミックス — 「音が安っぽい」と感じたら

一括描画は全楽器が無処理で中央に集まるため安っぽく聞こえやすい。チャンネルごとに
ステム描画し、パート別に処理してから混ぜると質感が大きく上がる。

- 歪みギター: asoftclip（tanh）で追い歪み＋キャビEQ（75 Hz 以下と 6.8 kHz 以上を切り、
  300 Hz を少し引く、3 kHz を少し上げる）。リズムギターは左右ダブルトラック
  （片側 11 ms 遅延＋薄いコーラスで別テイク感を出す）。
- ベース: 軽い飽和＋コンプ（acompressor の threshold は線形値。-20 dB = 0.1）。
- ドラム: コンプ＋高域シェルフでアタックを立てる。
- 空間: ノイズから生成した短い IR（afir）で各ステムに薄くリバーブを送る
  （-17〜-27 dB）。ドライ一辺倒が「安っぽさ」の主因のひとつ。
- 音源の差し替えも効く場面がある（台帳の GeneralUser GS はバンド編成で低域が厚い）。

### 手順4c: 実録サンプル楽器

ギター以外の楽器も実録サンプルで鳴らせる（カリンバ、アコギ2種、ピアノ、マリンバ、
木琴、グロッケン、ハープ、弦セクション、フルート、チェロ、コントラバス、
ベース2種、バリトンサックス等。全て CC0/CC-BY で検品済み）。
対応表・出所・ライセンス・音域は `references/instruments.md` の台帳に集約する。

鳴らし方:

1. 曲のステム MIDI をチャンネルごとに分ける（曲フォルダの prep/produce スクリプト）。
2. ステム MIDI → 音符イベント JSON（`scripts/dump_events.py`）。
3. 楽器ごとに描く: SFZ 楽器とフォルダ楽器は `scripts/render_sfz.py`
   （SFZ の #include・default_path・ファイル名解決、フォルダ内の音名読み取り、
   ベロシティ層・ラウンドロビン、oneshot/sustain の2モードに対応）。
   SF2 楽器（ピアノ）は FluidSynth でステム MIDI を直接描く。
   エレキギター DI は手順4d（`references/guitar.md`）。
4. ステムを手順4b のミックスに合流させる。

使い分けの目安:

- 主旋律: カリンバ、フルート、チェロ、ピアノ（forge）など実録の単音楽器が映える。
- 伴奏: アコギ（Emily / Shinyguitar）のアルペジオ、ハープのグリッサンド的ラン。
- 低域: マリンバ（柔らかい基礎）、コントラバス弓/ピチカート、エレキベース（バンド系）。
- 彩り: グロッケン（メロディのオクターブ重ね）、木琴、チューブラーベル（場面転換の一撃）。
- 面: バイオリンセクションのサステイン（パッド）、バリトンサックスの太いライン。

注意: VSCO 2 CE のマレット類はサンプリング間隔が疎い（5〜7半音）。移調で補完するため
近傍の音は実在感が高いが、大きく外れた音域は無理に使わない。SFZ には演奏ノイズの
region が混ざるものがあるため、render_sfz.py はパスに noise を含む region を自動で除外する。
実証デモ: 9楽器の小品（`~/workspace/midi-bgm/instrument_garden/`、環境側の実例）。

### 手順4d: ギターの音作り

エレキギターは GM の歪みプリセットが最も電子音感が強い。実録 DI サンプル
（Karoryfer Black And Green Guitars、CC0）を自作レンダラーで鳴らし、アンプ歪み＋
キャビEQ を後段で掛ける方式を使う。大原則は「DI → アンプ → キャビネット」の
信号順序で、歪み処理は必ず4倍オーバーサンプリングを挟む。
詳細（素材の調達と検品、和音化、歪み量の目安、ジャンル別レシピ、トラブル対応）は
`references/guitar.md` に集約する。ギター中心の曲では必ず併せて読む。

### 手順4e: ギター音色プリセット（guitar_fx.py）

ギターの音色は `scripts/guitar_fx.py` のプリセットで名前指定できる。DI 波形に対して
`python3 scripts/guitar_fx.py <preset> <in.wav> <out.wav> [--addon delay_375 ...]`。
ミックス内では PRESETS の "pre" チェーンを `[in]...[out]` で挟んで使う。
リバーブ系（surf/ambient/shoegaze）は生成 IR を使うため CLI 経由のみ。

- 素直系: clean / twang（明るい締まった音） / lofi（帯域を絞る＋ビブラート）
- 歪み系: crunch（軽い）/ overdrive（中域押し出し）/ blues（温かい軽歪み）/
  distortion（標準1段）/ lead_drive（2段・リード用）/ fuzz（ハードクリップ）/
  metal（中域スクープ）
- モジュレーション系: chorus_clean / flanger_clean / phaser_crunch / trem_drive
- 空間系: surf（スプリング強め）/ ambient（ディレイ＋ホール）/ shoegaze（ファズ＋ホール）
- 後段に足せる単体: chorus / flanger / phaser / tremolo / vibrato /
  delay_375 / delay_500 / slapback / presence / darken

歪み段は全て 4 倍オーバーサンプリング後にクリップする（素の asoftclip は
エイリアシングでジャリつく）。新しい音色が要る場合は既存チェーンの
boost/threshold/EQ を変えてプリセットとして追加し、この一覧にも足す。

## 手順5: 部分修正

直したい箇所は仕様書の該当フレーズ（数小節）だけを書き換えて、手順3→4を再実行する。
再生成は数十秒で終わるため、試聴→修正の反復を前提とする。
修正前と修正後の両方の OGG と仕様書を残し、何を変えたかをフォルダのメモに1行残す。

## 手順6: 納品ゲート

完成判定は作曲者の自己チェックだけにしない。render.py が次を機械確認する:

- (a) LUFS が -14 ± 0.5
- (b) トゥルーピークが -1 dBTP 以下
- (c) 低域比・スペクトル重心が同場面基準の許容幅内（低域比 ±15pt、重心は基準の 0.5〜2.0 倍）
- (d) 長さが仕様どおり（仕様の概算 −4秒〜+7秒。音源のリリース/リバーブの尾が付く分は上側に許す）
- 記譜: 主題の出現と戻り、音域（check_midi.py）

外れた項目は、記譜の問題なら作曲（手順3）へ、音響の問題ならマスタリング（手順4）へ差し戻す。
ゲートの許容幅は仕様書の `gate` で曲ごとに上書きできる。
最後はユーザーの試聴で確定する。

## 手順7: 音源の採用と台帳

使える音源は `references/instruments.md` の台帳に名前・ライセンス・出所を記録したものだけとする。
新規音源の採用条件: (1) ライセンスと出所を確認して台帳に記録すること（有料販売する
ゲームに収録できる条件であること）、(2) 同じ MIDI を描いて計測し、帯域比・重心が
現行セットより基準に近いこと。実録サンプル楽器の追加は「ライセンス確認→
**Release ZIP / 公式 tarball で取得**（git クローンはバイナリ破損の教訓あり、
guitar.md の検品節参照）→波形検品→試し鳴らし→台帳登録」の手順で増やせる。

実測上の注意: 音源の差し替えだけでは低域比はほぼ動かない場面が多い
（ピアノ主体の場面で同一 MIDI 38.7% → 35.3%）。低域は手順3の編成と手順4の EQ で作り、
音源差し替えは質感とダイナミクスの改善手段と位置づける。ただしバンド編成では
音源選びが低域にも大きく効く実測もある（FluidR3 16.4% → GeneralUser GS 36.4%）。

## ループ型の扱い

- ループ曲は頭と尾が同じ進行・同じエネルギーで接続するよう仕様で設計する。
- マスタリング後に仕様の長さで切り詰め（音源の尾は次の周回に重なる前提）、
  末尾2秒と先頭のクロスフェードを必須とする（render.py --loop が生成する）。
- 継ぎ目の合否は、継ぎ目前後の 100ms 窓 RMS の段差をクロスフェード無しと比較して判定する。
  実測では、曲形式の曲という条件でも段差 49.5 dB → クロスフェード後 9.2 dB まで下がった。
  段差が残る場合はクロスフェードを伸ばすのが効く（250ms で 6.2 dB → 0.13 dB まで
  下がった実測がある）。段差がゼロでないこと自体は直ちに不合格ではないが、
  不可聴かどうかは試聴で確かめる。
- ループ型の曲を初めて作るときは、試作1曲で継ぎ目を計測してから本番に入る。

## 記録

- 曲ごとに、仕様決定から納品までの実時間と手戻り回数を render_report.json とメモに残す。
- 所要の目安は「仕様決定から初回レンダリングまで1曲15〜30分、部分修正は1回あたり数分」
  だが、これは最も易しい場面1曲だけの試算である。場面ごとの実測で目安を更新する。

## 既知の限界

- 無料音源の音色の質感そのもの（1音の実在感や表情）は数値で測れず、天井が残る。
  帯域・音量・重心は測定と補正で基準に寄せられるが、「並べて遜色ない」の最終判定はユーザーの耳。
  天井を超えるには有料音源か生成AIとの併用が要る。
- メロディの記憶性は最終的に作曲そのものに依存し、定型化だけで保証はできない。
  主題の戻りは機械確認できるが、良い主題かどうかは試聴で判断する。
  手順0の主題選別はこの担保を強めるが、校正済みの範囲は長調の主題曲のみで、
  選別の余裕は選ぶ側の譜面読みに左右される。
- 自作ピアノ（forge_piano）で改善できるのは主旋律ピアノの音色だけである。
- エレキギターは実録 DI＋自作レンダラー＋アンプ処理で GM を置き換えられる。
  ただしホロウボディの明るい音色が素材の個性として残る（guitar.md 参照）。
- 実録サンプルに無い楽器（金管の多く、ナイロンギター等）は GM のまま。
  特にナイロンギターは無料・複数ベロシティ層・ライセンス清潔な単音セットが
  見つかっていない。必要になったら手順7の手順で台帳を増やす。
