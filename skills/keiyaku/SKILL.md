# 契約数を増やす（keiyaku）

## なぜこのスキルがあるか

AI に「契約数を増やす方法」を聞くと、次の4つの失敗をしやすい。

1. **施策の羅列** — 「SNS 広告を強化」「LP を改善」「キャンペーン」。どの段階の何の数字を何 % 動かすのかが無い。
2. **詰まりを見ない** — 流入を増やせば契約が増えると考える。実際は申込フォームや初回体験で 8 割落ちている、ということが多い。
3. **解約を忘れる** — 有効契約数は「新規 − 解約」の積み上げ。月 5% 解約なら、月 100 件の新規では 2,000 件で頭打ちになる（定常状態 ＝ 新規 ÷ 解約率）。新規だけを追うと穴の空いたバケツに注ぐことになる。
4. **効いたか判定しない** — 施策後の数字が上がれば「効いた」とする。季節・広告費・母数の小ささによる偶然を切り分けない。

このスキルは、契約数を式に分解し、数字で詰まりを特定し、顧客の言葉で原因を確かめ、施策を「どの数字を何 % 動かすか」で書き、効果を統計的に判定する手順で、この4つを潰す。

## 全モードで守ること

- **目標の数字を1つに決める**。「契約数」が新規契約数か、有効契約数（ストック）か、売上（MRR）かで打ち手が変わる。曖昧なら最初に確かめる。
- **数字が無い所は推定と書く**。推定値は幅（例 申込率 2〜4%）で持ち、`推定` と明記する。業界の目安（`references/funnel.md`）は「データが無いときの仮置き」にだけ使い、実データがあれば必ず実データを使う。
- **詰まりは計算で決める**。感覚で「LP が悪い」と言わない。`scripts/keiyaku.py funnel` で各段階の落ち方と「目標値に届いた場合の増分」を出してから決める。
- **原因は顧客の言葉で確かめる**。数字は「どこで」落ちるかしか言わない。「なぜ」は解約理由・失注理由・問い合わせ・レビュー・インタビューの原文で裏づける。手元に無ければ集め方を提案する（`references/levers.md` 冒頭）。
- **ユーザーを騙して契約数を作らない**。ダークパターン、誇大表示、解約しにくい設計、同意の取り方の不備は、短期で数字が出ても提案しない。日本の法規制（景品表示法・特定商取引法・個人情報保護法など）に触れうる施策は `references/ethics.md` で点検し、該当しうる点を明記する。法的判断は断定せず、専門家への確認を勧める。
- **事実を作らない**。実績・導入社数・お客様の声・受賞歴などを、ユーザーの資料に無いのに文案へ書かない。

## 参照ファイル

| 内容 | ファイル |
|---|---|
| 契約数の式、ファネルの段階の切り方、指標の定義、データが無いときの仮置きの目安 | `references/funnel.md` |
| 段階別の施策カタログ（B2C／B2B）、原因の確かめ方 | `references/levers.md` |
| 仮説の書き方、優先順位づけ、A/B テストの設計と判定、テストできないときの検証 | `references/experiment.md` |
| やってはいけないこと、法規制の点検表 | `references/ethics.md` |
| 診断と施策計画の出力形式 | `assets/plan-template.md` |

計算は `scripts/keiyaku.py`（Python 3.8+ 標準ライブラリのみ）。`S` はこのスキルの `scripts/` の絶対パス。

```
python3 $S/keiyaku.py selftest                                   # 最初に1回。FAIL なら手計算で進め、その旨を書く
python3 $S/keiyaku.py funnel <段階.csv>                          # 段階別の転換率・離脱数・目標到達時の増分
python3 $S/keiyaku.py stock --active 1200 --new 100 --churn 0.05 --months 12 [--new-x 1.1] [--churn-x 0.9]
                                                                 # 有効契約数の推移と定常状態。新規増と解約減の比較
python3 $S/keiyaku.py ab-size --base 0.03 --mde 0.2              # A/B テストの必要サンプル数（1群あたり）
python3 $S/keiyaku.py ab-judge --a 3000 120 --b 3000 150         # A/B テストの判定（訪問数 契約数）
```

`段階.csv` の形式は `references/funnel.md` の「CSV の形式」。

## 3つのモード

| モード | いつ | 出力 |
|---|---|---|
| **診断** | 「契約数を増やしたい」「伸びない」と言われたとき | 契約数の式、ファネル表、詰まりの特定、原因の仮説（`keiyaku/diagnosis.md`） |
| **施策** | 診断の後、または「施策を考えて」と言われたとき | 優先順位つきの施策表と実行計画（`keiyaku/plan.md`） |
| **検証** | 施策の効果を測る・判定するとき | テスト設計、または判定と次の一手 |

通常は 診断 → 施策 → 検証 と続ける。診断を飛ばして施策を求められても、手順1〜3（式・ファネル・詰まり）だけは簡易にやってから施策に入る。各手順の「→」の後が、その手順で**必ず書き出すもの**。書き出していない手順は、やっていないものとして扱う。

## 診断（始める前に `references/funnel.md` を読む）

1. **目標と式を決める**: 目標の数字・期限・現在値を確かめる。サービスの売り方（セルフ申込／トライアル→有料／営業経由／店舗）からファネルの段階を決める。→ 「有効契約数 = 前月 + 新規（流入 × 転換率…）− 解約」の形の式と、段階の一覧
2. **数字を集める**: ユーザーのデータ（GA・CRM・決済・管理画面の CSV など）を読む。無い段階は推定の幅と `推定` を書く。期間（直近 3 か月など）とチャネル別の内訳があれば取る。→ 段階.csv（実データ／推定の区別つき）
3. **詰まりを計算する**: `keiyaku.py funnel` と `keiyaku.py stock` を実行する。「目標値に届いたら契約が何件増えるか」と「新規増と解約減のどちらが有効契約数に効くか」で、上位 1〜2 段階を詰まりとする。→ ファネル表、ストックの推移、詰まりの段階と増分の見込み
4. **原因の仮説を立てる**: 詰まりの段階について、顧客の言葉（解約理由・失注理由・問い合わせ・レビュー）と実物（LP・申込フォーム・料金ページ・オンボーディング・営業資料）を見て、原因を3つ以上挙げる。実物は開いて見る。Web なら申込完了まで実際に操作して手数・入力項目数・エラーを数える。→ 原因の仮説と、それぞれの根拠（引用・観察・数字）
5. **確認→保存**: 推定の多い段階、原因の決め手が無い点を、最大2問・選択式でユーザーに確かめる（AskUserQuestion）。`assets/plan-template.md` の「診断」形式で保存。→ `keiyaku/diagnosis.md`

## 施策（始める前に `references/levers.md` と `references/ethics.md` を読む）

1. **候補を出す**: 詰まりの段階・原因の仮説ごとに、`references/levers.md` の該当段階から候補を選び、このサービス固有の形に書き直す。カタログの言葉をそのまま書かない。→ 候補（各段階 3〜6 個）
2. **仮説の形にする**: 各候補を「〇〇（原因）なので、△△（施策）をすれば、□□（指標）が X% → Y% になり、契約が月 Z 件増える」で書く。Z は `keiyaku.py funnel` の数字から出す。→ 仮説文
3. **優先順位をつける**: 効果（Z）、確からしさ（根拠の強さ）、手間（人日・費用）で採点する（`references/experiment.md` の「優先順位」）。→ 施策表（上位から並べる）
4. **倫理・法の点検**: 上位の施策を `references/ethics.md` で点検する。当たった施策は直すか外す。→ 点検結果
5. **実行計画**: 上位 3 つまでについて、担当・期間・測る指標・判定の基準（いつ、何がどうなったら成功／中止）・必要サンプル数（`keiyaku.py ab-size`）を書く。サンプルが足りない施策は、検証方法を変える（`references/experiment.md` の「テストできないとき」）。→ `keiyaku/plan.md`
6. **制作物があれば作る**: LP の文案、申込フォームの改修案、メール文面、営業トーク、料金表など。作ったものは「どの仮説のための変更か」を添える。→ 制作物と対応する仮説

## 検証（始める前に `references/experiment.md` を読む）

1. **設計（施策の前）**: 指標・比較対象（A/B、前後比較、地域・期間で分ける等）・必要サンプル数・期間・判定の基準を、**結果を見る前に**決めて書く。→ テスト設計
2. **判定（施策の後）**: `keiyaku.py ab-judge` で差と信頼区間と p 値を出す。前後比較なら季節・広告費・価格・競合の変化を並べる。サンプル不足・期間不足・途中で止めた場合はそう書き、「効いた」とは言わない。→ 判定（効いた／効かなかった／判断できない）と根拠
3. **次の一手**: 効いた施策は全体に展開し、ファネルの数字を更新して次の詰まりを探す（診断の手順3へ）。効かなかった施策は仮説のどこが外れたかを書く。→ 更新したファネル表と次の施策

## 往復を減らす

- **質問は1つの会話で合計3問まで**、AskUserQuestion で選択式。データやファイルを見れば分かることは聞かずに見る。
- データが全く無くても止まらない。推定の幅でファネルを組み、「最初に計測すべき段階」を施策の1番目に置く。
- ユーザーが既に施策を決めている（「このキャンペーンの効果を見たい」）なら、診断は手順1〜3を簡易に済ませ、検証に入る。
