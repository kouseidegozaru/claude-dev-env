# 契約数を増やす（keiyaku）

契約数を式に分解し、数字で詰まりを決め、顧客の言葉で原因を確かめ、担当と期日のある検証計画にする。
手順は段0〜7。各段の「→」が**必ず書き出すもの**。書き出していない段はやっていないものとして扱う。

## 落とさない3つ

1. **実物を開き、申込完了まで操作して手数を数える**（LP・申込フォーム・体験予約・営業資料）。開けないときは「開けない」と書き、見たかのように書かない。
2. **数値はスクリプトで計算する。暗算しない**。スクリプトが「停止」「警告」を出したら、その理由を出力に書き、入力を直して再実行する。
3. **判定の言葉を縛る**。「効いた」は `ab-judge` が事前の標本数に届いて「有意に高い」を出した場合だけ使う。前後比較は既定で「判断できない」。

あわせて: ユーザーを騙して契約を作らない。実績・お客様の声・合格率などを資料に無いのに書かない。法的判断は断定しない。

## スクリプト

`S` はこのスキルの `scripts/` の絶対パス。最初に `python3 $S/keiyaku.py selftest` を1回。FAIL なら手計算で進め、その旨を書く。

```
python3 $S/keiyaku.py funnel <段階.csv> [--contract 段名] [--churn R --months M] [--pooled K] [--set 段名=率]  # 率・容量・n<30・増分（期限時点に換算）。--set は仮説値の増分
python3 $S/keiyaku.py stock --active N --new N --churn R --months M [--target T] [--arpu Y] [--exit 月=件数] [--cap N]  # 期限時点の有効契約数・月商・期間の売上、新規×K と解約率×K
python3 $S/keiyaku.py ab-size --base P --mde M --daily D          # 必要標本数と日数。8週超は「A/Bテスト不適」
python3 $S/keiyaku.py ab-judge --a N X --b N X --planned N [--observational]  # z 検定か Fisher、Newcombe 区間、SRM 点検（無作為でない群は --observational）
python3 $S/keiyaku.py before-after --before [N] X --after [N] X --ly-before [N] X --ly-after [N] X  # 前後比較と基準線（それぞれの1年前）
```

## 手順

**段0 受付**（`references/intake.md`）
目標の単位（契約数・純増・MRR・売上）、期限、業態、手元データ（期間・母数・欠損）、待ち・断りの件数を確かめる。データで分かることは聞かずに見る。欠けは最大3問に絞って選択式で聞き、答えが無ければ「仮定」と書いて進める。
→ 受付表（項目・値・出典か「仮定」）

**段1 分解**（`references/funnel.md` 1〜2）
業態の型で段を切り、CSV を整える（全角・桁区切り・欠損・重複・合計行を直し、直した箇所を一覧にする）。複数チャネル・複数拠点は別々に回してから合算する。
→ 式と段階.csv（実数／推定の区別つき）と修正一覧

**段2 詰まり特定**（`references/funnel.md` 3）
`funnel`（`--churn --months` つき）と `stock`（卒業・満期は `--exit`、定員は `--cap`）を回し、新規の増分と解約減の増分を**期限時点の有効契約数**で並べる。上限到達の段は「枠を増やす」を候補にする。n<30 の段は合算し、それでも30未満なら順位を付けず「定性で決定」。
→ ファネル表・stock の表と、詰まり上位1〜2段（増分の数字つき）

**段3 原因確認**（`references/levers.md` 0）
詰まりの段について、顧客の言葉（解約・失注理由、問い合わせ、アンケートの原文）と実物の操作で原因を3つ以上挙げる。手元に無い情報は集め方を書く。
→ 原因の仮説表（根拠: 引用・観察・数字）

**段4 施策の優先順位**（`references/levers.md` 1〜5、`references/experiment.md` 1〜2）
仮説の形（もし〜なら〜が X%→Y%、根拠は〜）で候補を書く。Y での増分は `funnel --set 段名=Y` で出す（比例で暗算しない。容量・n<30 で結果が変わる）。解約減の案は `stock --churn-x` で出す。`効果×確からしさ÷手間`（各1〜5）で並べ、効果は期限時点の増分から `experiment.md` 2 の表で機械的に入れる。上位3件を段5へ。
→ 施策表

**段5 倫理・法の点検**（`references/ethics.md`）
上位3件を点検する。該当する施策は直すか外す。計画に入れない。法的判断は断定せず専門家への確認を促す。
→ 点検結果（施策ごとに「該当なし」か「該当と対応」）

**段6 検証設計**（`references/experiment.md` 3〜5）
施策ごとに `ab-size --daily` を回す。8週以内なら A/B（判定は `ab-judge`）、超えるなら上流の指標・大きな変更・`before-after` に切り替える。判定基準と標本数は結果を見る前に決める。既に「効いた？」と聞かれた施策は、ここで `before-after` か `ab-judge` で判定し直す。
→ 検証設計（指標と分母・方法・標本数・期間・合格線・中止条件）

**段7 実行計画**（`assets/plan-template.md`）
テンプレートの計画表を埋める。担当・開始日・判定日・判定方法・合格線・中止条件・準備物・点検済みを全部書く。「点検済み」が空欄の施策は計画に出さない。最初の2週間に誰が何をするかを日付つきで書く。計測の穴（経路・理由・コホートが取れない等）は1番目の作業に置く。
→ 作業ディレクトリ直下の `keiyaku/plan.md`（指定があればそこ。冒頭1画面に結論・数字・最初の1手）

依頼者への回答は plan.md の要約で済ませず、そのまま会議に持ち込める形で書く: 結論3行 → 依頼者が挙げた案ごとの判断表（やる／試す／保留／やらない と理由の数字）→ 誰がいつ何をするか表 → 実行する人が得るもの・手放すもの。

## 往復と出力

- 質問は会話全体で3問まで。データが全く無くても止まらず、推定の幅と「推定」で進める。
- 使い手が既に施策を決めている（「この施策の効果を見たい」）なら、段0〜2を簡易に済ませ段6へ。
- 例: `references/examples.md`（小母数の B2B、満杯の教室、売上目標で決済 CSV だけ）。
